# Payments API 5xx

If you are paged for elevated 5xx on the payments API, the first thing to understand is that this service depends on the ledger service and on Redis, and in the vast majority of past incidents the root cause has been either Redis connection pool exhaustion or a slow query in the ledger service, so it is worth checking those two things before doing anything else. The dashboard is at https://grafana.internal/d/payments and the relevant panel is called "5xx by route".

To mitigate, you should first check whether a deploy went out in the last 30 minutes by running `kubectl rollout history deploy/payments -n prod`, and if there was one, roll it back with `kubectl rollout undo deploy/payments -n prod`, which usually takes about 90 seconds to take effect. If no deploy went out, check the Redis pool with `redis-cli -h payments-redis info clients` and if connected_clients is above 4500 out of the 5000 max, restart the pool by scaling the deployment down to 0 and back up, but be aware that this drops in-flight requests, so only do it if the error rate is above 5%. As mentioned above, the ledger service is the other common cause; check its p99 latency and if it is above 800ms, page the ledger on-call rather than continuing to debug payments.

If none of this works, escalate to the payments on-call lead in #payments-oncall and include the incident ID, the output of the two commands above, and a screenshot of the 5xx panel. Do not spend more than 15 minutes before escalating. Afterwards, file an incident report within 24 hours and add any new symptom to this runbook.
