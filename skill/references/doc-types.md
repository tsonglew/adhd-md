# 文档类型骨架

不同文档类型的最优结构不同。这里给六种常见类型的骨架。

> **这是可选骨架，不是必填表单。** 没有的内容就不写，不要写「无」（见 `antipatterns.md` X8）。

骨架只在 `level=deep` 时用于重排章节顺序。`light` 与 `standard` 不改动整体骨架。

## 通用原则

任何类型都遵守：**结论 → 怎么做 → 为什么 → 边界情况**。

绝大多数难读的文档顺序是反的：背景 → 原理 → 方案 → 结论。

---

## README

给第一次来的人看。目标是三分钟内让人跑起来。

```text
# 项目名
一句话说清这是什么、给谁用。

## 能干什么
3–5 条，每条一个能力，写结果不写实现。

## 装 + 跑（约 N 分钟）
1. …
2. …
最小可运行示例，能直接复制。

## 常用场景
2–4 个，每个给命令和预期输出。

## 配置
表格：参数 | 默认值 | 说明。

## 出错了看这里
症状 → 原因 → 解法。

## 深入
链接到其他文档，不在这里展开。
```

关键动作：把「安装」提到「特性」之前的诱惑要抵抗住 —— 读者得先知道值不值得装。但「能干什么」必须压到 5 条以内。

## 教程 / Tutorial

给要动手的人看。目标是每一步都不卡。

```text
# 做出 X（约 N 分钟）
读完你能做到什么：一句话。
前置条件：清单式，含版本号。

## 第 1 步 · 动词开头的标题
做什么 → 命令 → 预期看到什么。

## 第 2 步 · …

## 做完了
怎么验证成功。
下一步可以去哪。
```

关键动作：每步给**预期输出**。看不到预期输出的读者会卡住，而 ADHD 场景下卡住等于放弃。步骤标题用动词开头。

## API / 参考文档

给查东西的人看。目标是三秒定位。

```text
# 模块名
一句话职责。

## 速查表
表格：接口 | 用途 | 常用参数。放最前面。

## 每个接口
### `functionName(args)`
一句话作用。
签名 / 参数表 / 返回值 / 最小示例 / 常见错误。
```

关键动作：**速查表放最前**。参考文档的读者九成是来找一个具体条目的，不是来通读的。每个条目结构完全一致，便于跳读。

## ADR / 设计文档

给做决定和事后考古的人看。

```text
# 决定：我们选 X（不选 Y）
状态：已采纳 / 已废弃 · 日期。

## 结论
选了什么，一句话。

## 为什么
2–4 条理由，每条一行。

## 放弃了什么
备选方案 + 放弃原因，表格。

## 代价
接受了哪些坏处。这节不许省。

## 什么情况下要重新考虑
触发条件。
```

关键动作：标题里直接写出决定。`## 结论` 在 `## 背景` 之前 —— 半年后来考古的人要的是决定本身，不是当时的讨论过程。

## 运维手册 / Runbook

给凌晨三点被叫起来的人看。这是对可读性要求最苛刻的类型。

```text
# 处理 X 故障
## 先做这个
最能止血的一步，放在所有内容之前。

## 确认是这个故障
症状清单，能一眼比对。

## 处理步骤
- [ ] 可勾选的步骤，每步一个动作
- [ ] 每步给验证方法

## 没好？升级
找谁、怎么找、给什么信息。

## 事后
清理、复盘要记什么。
```

关键动作：用 `- [ ]` 复选框 —— 半夜处理故障时，工作记忆不可靠，勾选框把「我做到哪了」外置到纸面上。止血步骤必须在最前。

## 会议记录 / 笔记

原始记录通常是最乱的输入，收益也最大。

```text
# 会议主题 · 日期
## 结论与待办
- [ ] 事项 — 负责人 — 期限
（放最前，这是 90% 的人唯一会看的部分）

## 决定了什么
每条一行。

## 还没定
悬而未决的问题 + 谁来推进。

## 讨论过程
折叠。绝大多数人不看，但不许删。
```

关键动作：待办放最前，讨论过程折叠进 `<details>`。会议记录是 `level=deep` 最常见的适用场景 —— 通常需要整体重排。

## 类型识别

模型按下列信号判断类型，判不出就问用户，**不要猜**：

| 信号 | 可能类型 |
|---|---|
| 文件名 `README` | README |
| 有序步骤 + 大量命令 | 教程 |
| 大量函数签名 / 参数表 | API 参考 |
| 「决定」「方案」「权衡」「备选」 | ADR |
| 「故障」「告警」「回滚」「值班」 | Runbook |
| 日期 + 人名 + 零散要点 | 会议记录 |

判错类型比不判更糟 —— 会把 API 参考重排成教程，破坏跳读。
