# 评分细则

评分权重、扣分和封顶值以 `rule-definitions.json` 为唯一来源；下面的评分表由
`python3 scripts/build_rules.py` 生成，解释和算法说明保留在本文件。

`audit` 输出 0–100 的脚本分。文本与 JSON 都保留全部 findings；`scope` 只决定展示与覆盖统计，
总分始终按全文所有适用轴计算。`level` 决定适用规则和未判定项目。

## 总分公式

```
总分 = Σ(维度分 × 权重) − X 组扣分
维度分 = max(0, 100 − Σ命中扣分)
总分 clamp 到 0..100
```

| 维度 | 权重 | 为什么这么重 |
|---|---|---|
| 首屏结论力 | 18% | 读者在前 15 行决定去留，这里失败后面全废 |
| 分块粒度 | 18% | 段落长度是 ADHD 阅读成本的第一相关项 |
| 扫读性 | 13% | 决定「跳着读」能不能成立 |
| 句子负荷 | 13% | 单句认知负担 |
| 行动性 | 12% | 决定读完能不能立刻动手 |
| 排版一致性 | 13% | 噪音水平 |
| 活人感 | 13% | AI 味浓的写法，每一种都要读者多花一次注意力 |

X 组是**全局扣分**，最多扣 20 分，在加权求和之后减。

只有定义了评分组件的规则才改变分数。规则表中标为「不计分」的项仍可能需要自动修复、给出提示或人工判断；它们不会增加或扣减评分。

## 分档

| 分数 | 结论 | 建议动作 |
|---|---|---|
| 90–100 | 优 | 不用改 |
| 80–89 | 好 | 可选微调 |
| 60–79 | 可用但吃力 | 建议 `standard` |
| 40–59 | 需重构 | 建议 `deep` |
| 0–39 | 差 | 建议 `deep`，并考虑拆文件 |

## 脚本分 vs 完整分

脚本只能判定 `det` 与 `lint` 规则。`judge` 规则由模型补。生成表中另有「仅提示」和「自动修复」项；提示不扣分，自动修复项不会冒充已审计。

- `audit`（默认 `level=2`）输出的是**脚本分**。默认 both 覆盖 75 条规则，其中 23 条需模型判断、7 条仅提示、2 条只由 `fmt` 自动修复、1 条由 `verify` 处理；数量从规则源按 `level` 和 `scope` 计算。未判定不等于通过，提示项不产生分值。
- 报告里的脚本分不显示优/好档位；它没有包含人工判断，不能代表完整评价。模型补充判断后分数可能下降。
- `--min-score`：用脚本分做 CI 门禁。可复现、无模型依赖、无网络。
- 模型跑完整评分时，必须逐条给出 `judge` 项的判定与依据（`文件:行`），不许只报一个总分。

两种分数在报告里分开列，不混为一个数字。**把脚本分说成最终分**是这个 skill 最容易犯的诚信错误。

### H1 的脚本判定是代理指标

脚本这样判「首屏有没有结论」：取第一个 H2 之前的内容，命中任一即通过 —— 标题含 TL;DR 类词、有 ≤5 条的要点列表、或第一段是 ≤3 句且 ≤80 字 / ≤40 词的短结论。

第一段以背景铺垫或会议元信息开头（`随着`/`近年来`/`众所周知`/`今天下午`/`本次会议`/`as the`/`in recent years` …）时不算通过，且**不再往后找** —— 否则文档中段任何一个短句都会被误判成首屏结论。

这只是代理指标。「这段到底是结论还是铺垫」最终要模型判断（S4/S5/H3）。

### X2 只看纯正文章节

碎片化的平均节长只统计**不含代码块、不含复选框列表**的章节，且至少要有 3 个这样的章节才计算。

原因：运维手册每步一节、每节一条命令，是正确结构而不是碎片化。X2 要抓的是「把叙述剁碎成一堆两行小节」，不是「步骤文档」。

阈值按语言分：中文 40 字，英文 25 词。英文一节 25 词约等于两句话，再高就会误伤合法的步骤文档。

## 前后对比要报什么

`report OLD NEW` 至少输出：

1. 总分 before → after，以及每个维度的 delta
2. X 组扣分 before → after（**after 的 X 扣分必须为 0**，否则视为优化失败）
3. `verify` 结论：通过 / 失败 / 无法判断；列出失败、警告和无法判断项，不把有警告的报告写成全部保全
4. 改动统计：段落数、句数、新增句数、搬移块数、折叠块数

只报总分上升是不够的。总分上升 30 但 X 扣分从 0 涨到 12，说明是拿过度格式化换来的分。
